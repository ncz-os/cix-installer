# Platform split: COMMON versus platform-unique build environment

Status: design (phase A) plus the non-moving enforcement of phase B. The physical
move (phase C) is specified here and lands on a branch based on the dual-arch
release branch. Machine-readable source of truth: `docs/platform-inventory.tsv`.

## 1. Why

The installer builds two products from one tree: `sky1-arm64` (Radxa Orion O6N /
CIX Sky1, Debian forky arm64) and `amd64` (Apple T2 MacBooks, ASUS/NVIDIA, generic
x86; feature tags `t2` and `nvidia-cuda` live inside this platform). Nothing in the
tree says which file belongs to which. Consequences seen in production:

* `post-install/run-all.sh` ran all 83 numbered hooks on every platform and relied on
  each hook to self-gate. About 60 hooks mention an architecture; only about 18 had
  an explicit arch check. The Sky1 hook `36-telemetry` enabled `serial-getty@ttyAMA0`
  on amd64 and the machine hung at "userspace". `12-sky1-firmware`, `83-panthor-gpu`
  and `15-mesa-sky1-pin` are further examples of Sky1 code with no structural gate.
* `build/` (130+ files) mixes shared tooling with Sky1 kernel and DKMS tooling and
  amd64 kernel staging; `assets/` (1,772 tracked files) mixes Mali/NPU/VPU blobs with
  T2 DKMS sources and NVIDIA keyrings.
* `manifests/desktop.pkgs` is implicitly arm64 and `desktop-amd64.pkgs` is a full
  copy, so divergence is invisible.

Goal: every file is classified at commit time, platform code cannot silently run on
the other platform, and the classification is checked mechanically.

## 2. Classes and features

| class   | meaning |
|---------|---------|
| `common` | correct and useful on every platform, or an arch-neutral mechanism |
| `sky1`   | belongs to `sky1-arm64` only |
| `amd64`  | belongs to `amd64` only |
| `mixed`  | one file that carries common logic and platform logic; kept whole, listed on every platform, flagged for a later split |

Feature tags (`t2`, `nvidia-cuda`) appear in the `feature` column of amd64 rows. They
are informational: one amd64 image serves T2 Macs, ASUS/NVIDIA boxes and generic x86,
and each feature hook decides at runtime from hardware. They are not separate
platforms and do not get their own hook lists.

Classification rule used for the first inventory: a hook is `sky1` or `amd64` only if
running it on the other platform is a no-op or writes only other-platform artifacts.
Anything that does useful generic work next to platform work is `mixed`, not
guessed into a platform. That keeps phase B a listing and gating change.

## 3. The inventory

`docs/platform-inventory.tsv`: `path<TAB>class<TAB>feature<TAB>reason`.

* A path ending in `/` is a directory-prefix row; the longest matching row wins, so a
  directory can be `sky1` with an exact-path `common` or `amd64` override
  (`assets/kernel/` is `sky1`, `assets/kernel/t2smc/` is `amd64`+`t2`).
* Hooks (`post-install/NN-*.sh`) must have their own exact row.
* Snapshot: 42 common, 14 mixed, 22 sky1 and 5 amd64 hooks; 317 rows cover all 2,500+
  tracked files. `assets/sky1-firmware/` is git-ignored blob input and is classified
  `sky1` so the rule survives the move.
* Evidence per row is the `reason` column: what the file touches (packages, device
  nodes, paths), and whether a guard exists.

## 4. Target layout (phase C)

```
common/
  post-install/        common + mixed hooks, run-all.sh, lib/, keyrings
  manifests/           *.pkgs shared closure, firmware.pkgs, firmware-bom.allow
  assets/              branding, screensaver-chooser, singularity patches, ...
  preseed/  build/  tests/  tools/  scripts/  packaging/   (shared library and gates)
platforms/
  sky1-arm64/
    post-install/      sky1 hooks
    hooks.list         explicit ordered list: common + mixed + sky1 hooks
    manifests/         package delta (see 6)
    assets/            mali, panthor, npu, vpu, cix-*, sky1-firmware, kernel overlays
    build/             kernel debs, DKMS debs, NPU SSDT, OTA, kvm-install-gate (arm64), verifiers
    release.conf.d/    overlay for release.conf
  amd64/
    post-install/      amd64 hooks (t2, gpu-accel, kernel)
    hooks.list
    manifests/  assets/ (t2 DKMS, apple-t2 firmware, nvidia keyring)  build/ (publish/stage amd64 kernel, kvm-install-gate-amd64)
    features/          t2/  nvidia-cuda/   (data + notes; hooks stay hardware-detected)
```

Files whose class is `mixed` move to `common/` unchanged, flagged by an
`NCZ-MIXED-HOOK` marker; splitting them is a follow-up (`TODO(platform-split)`).
The on-image and `ncz-payload` paths do not change: builders stage
`common/<x>` and `platforms/$PLATFORM/<x>` into the same destination the tree
uses today, so late.sh, extract-rootfs.sh and every hook see identical paths.

## 5. Hook lists (live in phase B)

* `post-install/hooks.list.<platform>` is generated by `build/gen-hooks-lists.sh`
  from the inventory (common + mixed + own-class hooks, filename order = execution
  order). Never edited by hand; `make lint-platform` fails if stale.
* `run-all.sh` picks the platform from `NCZ_PLATFORM`, else the arch it already
  computes (`NCZ_TARGET_ARCH`, the `BUILD_ARCH` stamp, `dpkg`): arm64 gives
  `sky1-arm64`, amd64/x86_64 gives `amd64`. It then removes from its plan every hook
  not on the list and logs each removal (`PLATFORM-SKIP: <hook>`).
* The list only removes. Baked-mode and component-selector filters are unchanged,
  and platform-skipped hooks are not reported as ORPHAN.
* Fallbacks that keep old payloads working: no list on disk, an unreadable list, an
  undetectable architecture, or `NCZ_HOOKS_LIST=none` all mean the previous
  behavior (every hook is a candidate). The old ISO builder `build-iso.sh` copies
  only `*.sh`, so it ships no list and behaves as before; `build-iso-di.sh` and
  `build-installer-image.sh` copy the whole directory and get the lists.
* Defense in depth: every `sky1`/`amd64` hook also starts with an
  `NCZ-PLATFORM-GUARD` block (exits 0 on the other architecture, proceeds when the
  arch is undetectable). A list is the routing; the guard protects a hook run by
  hand or from an unlisted path.
* 70-bootloader and 99-diagnostics run from run-all's EXIT trap and are common/mixed
  on every list.

## 6. Manifests: common + platform delta

Today `desktop.pkgs`, `installer-base.pkgs`, `rescue.pkgs` (arm64, implicit) and
their `-amd64` twins are full, separate closures. Phase B adds a lint instead of
changing them: a package present in one platform's list and absent from the other
must have a row (with reason) in `docs/manifest-divergence.tsv`. The first pass
recorded 32 such packages (Sky1 VPU ffmpeg, T2 Thunderbolt `bolt`, microcode,
syslinux, ...), and it flags the two known parity gaps for the release branch
(`ncz-singularity-desktop`, `swayidle`/`swaylock`).

Phase C target: `common/manifests/<name>.pkgs` (intersection) plus
`platforms/<p>/manifests/<name>.delta` with `+pkg` / `-pkg` lines; a small merge
step in the build writes `build/<name>.<platform>.pkgs`. Acceptance: the merged sorted
set equals today's file for each platform, byte for byte after normalization.

## 7. Selecting the platform in the build

`Makefile` already has `ARCH`. Phase C adds `PLATFORM := $(if $(filter arm64,$(ARCH)),sky1-arm64,amd64)`
and builders take `PLATFORM_DIR=platforms/$(PLATFORM)`. `make lint-platform`,
`make gen-hooks-lists` and `make test-platform` exist now; `make image` runs the
lint before the input checks.

## 8. Rules for adding files

1. Add a row to `docs/platform-inventory.tsv` in the same commit (`common`, `sky1`,
   `amd64` or `mixed`; feature `t2`/`nvidia-cuda` on amd64 rows). Use a directory
   prefix row only for a homogeneous directory.
2. New hook: exact row, then `make gen-hooks-lists`. A `sky1`/`amd64` hook starts
   with the `NCZ-PLATFORM-GUARD` block (copy from any existing platform hook). A
   `mixed` hook carries `# NCZ-MIXED-HOOK: <what is platform-specific>`.
3. A COMMON hook must not mention platform tokens (`build/platform-deny-patterns.txt`:
   sky1/cix/mali/panthor/aipu/amvx/ttyAMA..., t2/apple/nvidia/cuda/amdgpu...). If the
   token is deliberate (message text), add a reasoned row to
   `docs/platform-deny-exceptions.tsv`; otherwise move the code to a platform hook.
4. A package in only one platform's manifest needs a reasoned row in
   `docs/manifest-divergence.tsv`.
5. Stale rows (file removed, exception no longer matching) fail the lint, so
   the files cannot rot.

Enforcement points: `make lint-platform` (also part of `make image`), unit tests
`build/test-platform-lint.sh` (`make test-platform`), and the CI job that should run
both on every push.

## 9. Migration and compatibility plan

* Phase A/B (this branch): no file moves. Adds the inventory, lists, lint, guards,
  markers and tests; changes `run-all.sh`, the 27 platform hooks (guard block at
  the first code line) and 14 mixed hooks (one comment line).
* Phase C (after `release/dual-arch-2026-09-29` exists): `git mv` per inventory,
  so `git log --follow` keeps history. `tools/platform-split-move.sh` is scripted and
  re-runnable: it moves files, then rewrites every referencing path in `Makefile`,
  `build/`, `preseed/late.sh` and `extract-rootfs.sh` payload staging, docs, tests,
  `.gitignore` (the `sky1-firmware` blob directory moves under
  `platforms/sky1-arm64/assets/`) and CI files. Compatibility symlinks at the old
  paths are kept for one release only where a caller cannot be rewritten (for
  example a fleet host script); each is listed in `docs/PLATFORM-SPLIT.md`.
* Both ISO/image builders (`build-iso-di.sh`, `build-installer-image.sh`) must keep
  producing the same payload under the same names.
* Proof that nothing changed: before the move, capture for each platform a payload
  manifest (sorted `path sha256` of every asset, hook and manifest the builders
  copy, plus `make -n` for both ARCH values); after the move, the normalized lists
  must be equal. Then the unit tests and one KVM install gate per platform on idle
  hosts.

## 10. Risks and rollback

| risk | mitigation |
|------|------------|
| A hook wrongly classified sky1/amd64 stops running on a platform that needs it | conservative rule (mixed when unsure); `PLATFORM-SKIP` lines make every removal visible in the install log; `NCZ_HOOKS_LIST=none` restores legacy behavior with no rebuild |
| Guard block breaks a hook | inserted before the first code line, exits 0 only for the other arch, proceeds on unknown; hooks pass `bash -n`; existing unit tests unchanged |
| Lint false positives | reasoned exception files, stale-row detection, tests for both directions |
| Move breaks a path reference | scripted rewrite plus payload-manifest equality, compatibility symlinks for one release |
| Conflict with the release branch | phase B touches new files, `run-all.sh`, hooks (top-of-file comment/guard) and two Makefile hunks only |

Rollback: phase B is one revertable commit series; reverting it restores every hook
byte for byte. Phase C is one rename commit plus the rewrite commit on its own branch,
never merged to main until both platform image gates pass.
