## What this release fixes

### Nine post-install hooks never ran on ANY baked install

`run-all.sh` builds its execution plan from allowlists. Under `NCZ_BAKED=1`
— every `--mode full` install — a hook in neither list was silently skipped:
no log, no warning, no progress tick, and the install still reported success.

Dropped hooks: `12-sky1-firmware`, `15-mesa-sky1-pin`, `16-mesa-gpu-2613`,
`23-base-apt-sources`, `27-net-caps`, `32-quadlet-shim`, `33-network`,
`39-usb-gpt-autofix`, `44-rtc-sync`.

Two were confirmed broken on hardware, and both had previously been
re-diagnosed as hardware faults:

* **VPU could not decode or encode.** `12-sky1-firmware` never ran, so
  `/lib/firmware` held **zero** `*.fwb` while all 16 codec blobs sat unused in
  the installer asset tree. With the firmware in place the Linlon v5276
  enumerates 8 decode formats and hardware H.264/HEVC encode both work.
* **Every fresh flash booted ~2 years in the past.** `44-rtc-sync` never ran,
  so `hwclock` was absent and the RTC kept its 2024 firmware default, breaking
  TLS-validating tools until NTP won the race.

A plan-time **ORPHAN audit** now names any hook present on disk but in no
execution list, so a future omission is visible in the install log instead of
shipping a dead subsystem. It caught its first real regression immediately.

### Accelerator and driver fixes

* **NPU userspace was empty.** `88-noe-umd-venv.sh` globbed
  `NOE_Engine-*.whl`, but the vendor ships the PEP-427 name
  `noe_engine-3.0.0-…whl`. An unmatched glob passes through literally and `uv`
  rejects the whole invocation, so libnoe, numpy **and** pip were all skipped
  together — one bad glob emptied the venv. The venv now also re-syncs when
  `cix-noe-umd` is upgraded, instead of staying stale forever.
* **VPU ran the older in-tree driver.** The DKMS version passed by the hook
  disagreed with `PACKAGE_VERSION` in `dkms.conf`, so the build ran in a
  directory that never existed. The version now comes from the conf.
* **Two panthor modules in one directory.** The "did DKMS produce a module?"
  test only looked for the uncompressed name, so the prebuilt fallback fired
  even after a successful DKMS build.
* **Three apt guards were inert.** `$(… | grep -c X || echo 0)` yields `"0\n0"`
  on the no-match path, because `grep -c` prints `0` *and* exits 1. Every
  guard took its failure branch on the safe path — `python3-numpy` was never
  installed despite the log reporting zero removals.

### Hardware coverage

* **WiFi/Bluetooth firmware now ships.** cixmini's MT7922 blobs were present
  on the build host but owned by **no package** — hand-dropped at some point —
  so a clean install shipped zero MediaTek firmware and WiFi was dead. Added
  `firmware-mediatek`, `firmware-brcm80211`, `firmware-atheros`,
  `firmware-iwlwifi`, `firmware-ath9k-htc` (~99 MB) to cover the radios that
  realistically appear in an M.2 slot, including Orange Pi 6.
* **Diagnostics.** `alsa-utils` and `v4l-utils` — `aplay -l` and `v4l2-ctl`
  were both missing on an image whose purpose is accelerator support.
* `util-linux-extra`, for `hwclock`.

### Regression fixed inside this release cycle

v11 shipped a **worse** bug than the one it fixed: promoting the two orphaned
hooks into the *fatal* REQUIRED phase meant `33-network` — which exits 1 by
design on this SKU, because Singularity uses `sinty-nmd` and 20-desktop.sh
purges NetworkManager — aborted **every** install at finish-install. Both
hooks now run in the fail-tolerant phase, and `33-network` self-skips cleanly.

## Known issues

* **Models are not on the ISO by design.** `/opt/ncz/models` is empty after a
  fresh install; install `ncz-model-nomic-embed` (or another tier) from the
  apt repo. NPU inference fails with `noe_load_graph` until a model is present
  — that is a missing model, not a broken NPU.
* `47-embedkit.sh` exits 2 while still reporting `embedkit import OK`;
  non-fatal, the installer continues.
* `12-sky1-firmware` warns about `arm/mali_csffw.bin` being absent. The GPU
  works: mali loads `arm/mali/arch12.8/mali_csffw.bin`. The hook's expected-path
  list predates the arch-specific layout.
* The KVM install gate (`build/kvm-install-gate.sh`) is committed but does not
  yet complete unattended: QEMU's `virt` machine exposes one PL011, while the
  ISO's install entry targets `ttyAMA2` (the O6/O6N port), so d-i falls back to
  the video console and the run is unobservable. v12 was validated on metal.
