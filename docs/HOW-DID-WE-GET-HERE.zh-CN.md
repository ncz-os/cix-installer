# 我们是怎么走到这一步的

> **🌐 语言：** [English](HOW-DID-WE-GET-HERE.md) · 简体中文

NCZ-OS 26.7 "Maximilian" 与上一个版本几乎判若两物。差异的绝大部分来自三项变更：
内核从 7.0.12 迁移到 7.2、基础发行版从 Ubuntu 换成 Debian Forky、桌面从 X11 上的
XFCE 换成 Wayland 上的 Singularity。

每一项代价都不小。本文说明每项变更的成本，以及为什么它依然是正确的选择——好让
接触到当前代码树的读者，不必再从提交记录里做考古来还原这些推理。

---

## 为什么要做这些事

简短的答案是：**Sky1 主板上有 GPU、有 VPU、有 NPU，而它们一个都不可用。**

不是缺失，是**不可用**——这个区别正是本次发布存在的全部理由。厂商 BSP 会痛快地
给你一个 `/dev/aipu`、一次干净的 probe，以及 `dmesg` 里一行宣告 Zhouyi V3 NPU 的
横幅；会给你 Mali 的 DRM 设备；会枚举出 `/dev/video0`。规格表上每一格都能打勾。
然后你真去跑一次推理，上下文初始化失败；真去解一帧码，发现没有固件；真去查你那台
"已加速"的桌面到底跑在什么上面，结果是一个从未拿到 GLES 上下文的合成器背后的软件
渲染。

这三项变更各自拆掉了其中一堵墙，而且**没有任何一项能单独奏效**：

- **内核必须迁到 7.2**，因为 `mali_kbase` 的 Mali-G720 驱动移植和 DisplayPort
  链路训练修复都在那里。在 7.0.12 上，唯一的 GPU 路径是内核自带的 panthor 加
  Mesa panvk，在这块硬件上最终落到经由 zink 的 OpenGL 2.1。一个以 GPU 为核心卖点
  的发行版，不可能建立在"能力上限 GL 2.1、而硅片本身支持 GLES 3.2"的栈上。
- **基础发行版必须换到 Debian**，因为 ARM 在 Debian 是一等公民，在 Ubuntu 是二等
  公民。当你需要的每一个包都是 arm64、而一半的构建时间都在和软件仓库较劲时，
  稀薄的 ARM 镜像覆盖就不再是表面问题。
- **桌面必须换到 Wayland**，因为这块硅片上的加速路径**就是** Wayland 合成器上的
  GLES。X11 客户端只能经由 Xwayland 抵达，更慢——而且未必抵达得了。继续用 XFCE，
  等于把一台全部卖点都在 GPU 上的硬件，装在一个结构上够不着这块 GPU 的显示栈里。

修好内核却保留 X11，GPU 依然够不着；修好桌面却停在 7.0.12，根本没有 `mali_kbase`
可用；两者都修却留在 Ubuntu，省下的时间又都花在为 arm64 包奔波上。这三项是**互为
承重结构**的——这正是它们必须一起落地的原因，也正是过程中让人觉得疯狂的原因。

## 1. 内核：从 7.0.12 到 7.2

<p align="center">
  <img src="../assets/branding/wallpaper/ncz-wallpaper-02-interstellar-gargantua-2k.jpg" alt="" width="780">
</p>

这是三者中难度最高的一项，差距很大，也是本次发布耗时如此之久的原因。

### 问题所在

Linux 主线目前还无法启动一个可用的 Sky1 桌面。但这并不等于说 Sky1 在主线中毫无
踪影：CIX 正在积极地把这个平台推向上游，核心 SoC 使能已经提交，并在陆续合入。主线
仍然缺少的，是一个桌面所需要的其余部分——显示、GPU、NPU、VPU，以及大量 SoC 胶合
代码——这些存在于一组针对特定上游基线维护的厂商补丁系列之中。重新变基这组系列，
并不是一次例行操作：

- 构建配方的 `SRC_URI` 中接入了 **176 个补丁**，而代码树里实际存在 **197 个**补丁
  文件。多出的 21 个已被取代或属实验性质，是刻意不予引用的。
- 补丁按 **`SRC_URI` 顺序**应用，**而非文件名顺序**。若干后期修补被穿插在系列的
  更早位置。按编号顺序应用会得到一棵编译不过的树。
- 移植期间上游基线移动了四次：`v7.2-rc4` → `rc5` → `rc6` → `rc7`，每次都是不同的
  SRCREV。每一次移动都要求对整个系列重新验证。

在 rc4→rc5 变基中带过去的 170 个补丁里，**169 个是逐字节一致应用的**。那唯一的
例外恰恰是这项工作的形状：变基的大部分是机械劳动，价值完全在于找出不机械的那一
小部分。

### 更糟的是

补丁系列与配方之间已经漂移。某个时点上，树里带着配方并未接入的补丁，而配方接入的
补丁却有文件缺失——**接入 171 个，应为 176 个，其中 5 个补丁文件完全不存在**。处于
这种状态的源码交付无法重建所发布的内核，这既是工程问题，也是**许可证问题**。

修复方式不是一次性的补救。`build/port-series.sh` 现在会解析配方的 `SRC_URI`、按
配方顺序应用系列，并在任何已接入的补丁无法应用时让构建失败。漂移在构建时即被捕获，
而不是几个月后由某个试图复现二进制的人发现。

### 究竟为什么要做

7.2 承载了当前的 Sky1 使能：DisplayPort 链路训练修复、完整的 `mali_kbase`
Mali-G720 驱动移植，以及启动告警清理。留在 7.0.12 意味着留在一个 EOL 内核上，
并放弃上述全部内容。

**26.7 只发布一个内核：`7.2.0-sky1-ncz`。7.0.12 通道已从镜像中移除**——它不是
回退方案，也不是救援内核。

## 2. 基础发行版：从 Ubuntu 到 Debian Forky

### 为什么

**ARM 在 Debian 是一等架构，在 Ubuntu 是二等架构。** Ubuntu 的 ARM 镜像覆盖更
稀薄，其周边生态默认以 x86 为前提。对一个立足点就是"带集成 GPU、VPU、NPU 的 ARM
硅片"的发行版而言，这是错误的地基。

第二个理由是下文第三项变更的连带结果：**Ubuntu 的血统是通过 XFCE 桌面继承来的。**
NCZ-OS 之所以对齐 Xubuntu 的软件包集合，是因为 XFCE 出自那里。一旦弃用 XFCE，这层
映射就不再带来任何好处，留在 Ubuntu 的理由也随之消失。

### 代价

关于包名、版本与仓库布局的每一条假设，都必须对着 Forky 重新核对。Forky 是 Debian
的 *testing*，因此它本身也在移动——这是刻意的选择，因为在这里，当前的 ARM 使能比
冻结的稳定性更重要。

安装程序现在会在安装过程中移除 `/etc/apt/sources.list` 并删除任何 Ubuntu 或
resolute 源文件，确保在 Debian 画像的镜像上，Ubuntu Ports 绝不会作为活跃回退残留。

---

## 3. 桌面：从 X11 上的 XFCE 到 Wayland 上的 Singularity

### 为什么

Sky1 上的加速图形路径是 **Wayland 合成器上的 GLES**。X11 客户端无法免费获得这条
路径——它们运行在 Xwayland 之下，落到更慢的路线上，前提是它们能跑起来。

继续用 XFCE，等于把一台主要卖点就是 GPU 的硬件，装在一个无法正确抵达该 GPU 的
显示栈上。

### 代价

**X11 是被完全移除，而不是"标记弃用但仍在"。** 这个立场比听起来更难，因为它会破坏
一切假定存在 X 会话的东西——GL 屏保是最典型的例子，`xscreensaver-gl` 本身就是一个
期待真实用户会话的 X11 程序。

Singularity 基于 labwc/wlroots，原生使用 Mali GLES。网络栈改用 `sinty-nm` 而非
NetworkManager，消息总线改用 `dbus-broker` 而非 `dbus-daemon`。

## 这件事花了多少

26.6 于 2026-07-20 发布。26.7 "Maximilian" 于 2026-08-18 发布。

| | |
|---|---|
| 自然日 | 29 天 |
| 有提交的活跃天数 | 24 天 |
| 提交数 | 422 |
| 变更文件数 | 1,792 |
| 新增行数 | 788,459 |
| 涉及的内核补丁文件 | 286 |
| 涉及的安装后钩子 | 65 |
| 涉及的构建脚本 | 41 |

上述三项变更全部落在这个窗口之内。

这一点值得直说，因为它同时也是本次发布承担的主要风险。一个发行版通常会把基础发行版
变更**或**桌面变更**或**内核变基分别排期——不会三件同时进行。每一项都会使另外两项的
测试面失效，因此在它们同时在途时，**没有任何固定参照点可供调试**：一次安装失败可能
来自内核、来自新基础、来自新桌面，也可能来自其中任意两者的相互作用。

代价在收尾时显现。有一个构建带着"在每台机器上都会中止的安装程序"发布了出去，之所以
流到硬件上，是因为当时没有自动化的安装门禁来拦截它——而这样一道门禁脚下的地面，已经
晃了整整一个月。该门禁现已存在（`build/kvm-install-gate.sh`）。从中该吸取的正确教训
是：当地基必须同时移动时，验收测试必须是**最后一个保持不动的东西**，而不是第一个被
推迟的东西。

## 两个 GPU 驱动都会发布

NCZ-OS 不在厂商驱动与开源驱动之间选边站。它**两个都发布**，由操作者选择：

| 驱动 | 软件包 | 角色 |
|---|---|---|
| `mali_kbase` | `cix-gpu-kmd`（DKMS） | **默认。** CIX 厂商 DDK。经由 `libmali` 提供 GLES 3.2 与 OpenCL。桌面就跑在它上面。 |
| `panthor` | `panthor-cix`（DKMS） | **可选。** 主线开源驱动，经由 Mesa PanVK 的 Vulkan 路径。 |

两者都会安装，并且在 `/etc/modprobe.d/ncz-gpu-drivers.conf` 中**都被列入黑名单**，
以免任何一个被意外加载——否则它们会同时认领同一个设备。真正绑定的那一个是显式选择的，
`ncz-gpu-select` 用于在两者之间切换。

同时携带两者的理由是它们各有所长。`mali_kbase` 是当下经过验证的路径：它提供桌面所需
的 GLES 3.2，以及计算栈使用的 OpenCL。`panthor` 是生态的走向——它在主线、它开源、它是
通往 Vulkan 的路——但在 Sky1 上它仍在处理枚举问题，因为该主板经由 ACPI 而非设备树启动，
而主线 panthor 没有 `.acpi_match_table`。

只发布厂商驱动，会把发行版绑死在一个没有开源继任者的二进制上；只发布 panthor，则意味着
发布一个今天无法加速的桌面。同时携带两者的成本只是一次 DKMS 构建和一个黑名单文件，
换来的是：任何人都能在所发布的镜像上、无需重新构建，就在真实硬件上测试开源路径。

## 值得吗

<p align="center">
  <img src="../assets/branding/wallpaper/ncz-wallpaper-07-maximilian-blackhole-2k.jpg" alt="" width="780">
</p>

值得。证据是三个加速器现在确实都能工作，而且是在硬件上**实测**得出的，不是从一次
probe 推断出来的：

| | 之前 | 之后（O6N 实测） |
|---|---|---|
| **GPU** | 经 zink-over-panvk 的 GL 2.1 | **Mali-G720-Immortalis，GLES 3.2**，10 核，桌面真正获得加速——同时仍并行发布 panthor，见上文 |
| **NPU** | 能枚举，但无法完成任何推理 | 每 256 token 分块 **95.5 ms**，多次运行结果一致，中断计数正常增长 |
| **VPU** | 完全没有编解码固件 | **8 种解码格式**；H.264 与 HEVC 硬件编码在 720p 与 1080p 上均已确认 |

这就是回报。不是"驱动能加载"，而是**三个你真正调得动的加速器**，来自一个离线安装
镜像，装在一块出厂时上述功能全都不工作的主板上。

本项目为自己设定的标准写在驱动保真度文档里，值得在此重复一遍，因为正是它造就了
"之前"与"之后"两栏的差别：

> 一个设备节点、一次干净的 probe、一行打印出来的横幅，都不构成"加速器能工作"的证据。

上表"之后"一栏中的每一项，背后都有一个实际负载，而不是一行横幅。

### 前后对比

| | 之前 | 现在 |
|---|---|---|
| 内核 | 7.0.12（EOL） | `7.2.0-sky1-ncz`，单一通道 |
| 基础发行版 | Ubuntu | Debian Forky |
| 桌面 | X11 上的 XFCE | Wayland 上的 Singularity，原生 GLES |
| GPU | 内核自带 panthor | `mali_kbase` DDK，Mali-G720-Immortalis，GLES 3.2 |
| NPU | — | Zhouyi V3，每 256 token 约 95 ms |
| VPU | — | Linlon v5276，8 种解码格式，H.264/HEVC 编码 |

已在 Radxa Orion O6N 与 Minisforum MS-R1 上验证。Orange Pi 6 验证进行中。
