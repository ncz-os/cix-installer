# arm64 kernel pin: 7.3.3-sky1-ncz (r298) — APPLIED 2026-11-08

> **Status: applied.** The O6N boot test passed on 2026-11-08; the pin patch was
> applied with that date, and `docs/patches/arm64-kernel-733-pin.patch.in` and
> `build/test-arm64-733-pin-patch.sh` were deleted. The text below is the
> pre-application record.

The Sky1 7.3.3 kernel is built, gated and staged. The pin that makes arm64
images use it is kept as a patch template,
[`docs/patches/arm64-kernel-733-pin.patch.in`](patches/arm64-kernel-733-pin.patch.in),
and is not applied. It is a template because the pin records the O6N boot-test
date, which does not exist yet. The reason is the operator rule in docs/RC-DEFINITION.md: a
kernel is pinned only after it passes a hardware boot test, and this one has not
been booted on O6N yet. Until it is applied, `CURRENT_KVER_arm64` stays empty
and `build/check-kernel-lifecycle.py --arch arm64` (verify-kernel-default-policy
Check 11) refuses every arm64 build. `build/test-arm64-733-pin-patch.sh` checks
three things: the gate refuses arm64 on this tree, the patch applies, and with
it applied both arches pass the gate.

## Applying it (after the O6N test passes)

The patch has one placeholder, `@O6N_BOOT_DATE@`. It appears in the commit
message, the KERNEL-LIFECYCLE comments and `sky1-manifest.json` (note and
`hardware_boot`), and never in `manifests/`. Substituting the date therefore
changes no ledger and leaves `components.tsv` and `determinism.pin` valid; this
was checked on ULTRA.

```bash
git checkout -b hv/rc4-arm64-kernel-733-promote <this branch>
D=2026-MM-DD    # the date of the passing O6N boot test
sed "s/@O6N_BOOT_DATE@/$D/g" docs/patches/arm64-kernel-733-pin.patch.in > arm64-kernel-733-pin.patch
! grep -n '@O6N_BOOT_DATE@' arm64-kernel-733-pin.patch
git am arm64-kernel-733-pin.patch && rm arm64-kernel-733-pin.patch
git rm -q docs/patches/arm64-kernel-733-pin.patch.in build/test-arm64-733-pin-patch.sh
git commit -qm "kernel: drop the applied arm64 7.3.3 pin template and its test"
bash build/gen-base-pin.sh --check && python3 build/gen-components-registry.py --check \
  && python3 build/check-kernel-lifecycle.py --arch arm64
# then the RC-DEFINITION check list; update the rc4 row in docs/RC-DEFINITION.md
```
The kernel-ci registry entry moves r298 to `current`. The amd64 pin is not
touched.

## Lane fixes on this branch

A fresh build tree exposed three problems in the Sky1 kernel lane. Each fix
landed test first:

- `build/stage-kernel.sh` with `NCZ_SKIP_PACKAGING=1` (as `release-kernel.sh`
  calls it) failed after every gate had passed, on `ls build/kernel-debs/`
  under pipefail, when the tree had never packaged a kernel.
  (test-stage-kernel-skip-packaging.sh)
- `build/stage-accel-overlays.sh` had no `pahole` in the container, so with
  `CONFIG_DEBUG_INFO_BTF_MODULES=y` the Mali overlay failed ("pahole: not
  found"). It now uses the kernel's own `recipe-sysroot-native` pahole, and
  refuses up front when that pahole is missing. (test-stage-accel-overlays-pahole.sh)
- `build/host-ready.sh` looked for `config-7.3.0-sky1-ncz` in every staged
  release, so any kernel bump would have read as a stale pool. It now takes the
  file name from the manifest. (test-host-ready.sh section 13b)

Still open, not fixed here: `release-kernel.sh` regenerates
`kernel-manifest.json` only at step 7, but the overlay gate at step 4b
cross-checks it. On a KVER bump the lane therefore stops at 4b until the
manifest is regenerated. For r298 it was regenerated with the lane's own
`kernel-manifest.py gen` before re-running.
