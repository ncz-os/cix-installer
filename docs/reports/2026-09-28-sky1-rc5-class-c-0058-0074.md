### 1.5 The counted-reference contract — *what a re-port would have to honour*

If a re-port genuinely needed to expose a fwnode-keyed lookup on top of
the modern refcounted core, the contract would be exactly:

* **Acquirer:** the producer of the exported helper must call
  `drm_panel_get(panel)` before returning the matched panel from
  the list walk. The upstream `of_drm_find_panel()` does this at
  `drm_panel.c:491`; the upstream `find_panel_by_fwnode()` does
  this at `drm_panel.c:521`. Both follow the same pattern.

* **Releaser:** the caller of the exported helper must call
  `drm_panel_put(panel)` on every successful return, exactly once,
  on **all** exit paths. The two safe styles for the Sky1 linlon-dp
  caller are:
  - install `drm_panel_get` / `drm_panel_put` symmetry around the
    local `struct drm_panel *edp_panel` and replace the unconditional
    `return PTR_ERR(edp_panel);` with `goto put;` paths that drop the
    reference; or
  - use `devm_drm_panel_attach()` and store the `struct device *`-managed
    refcount, which is what mainline drivers standardise on (no manual
    `drm_panel_put` on error paths).

* **Non-fatal `EPROBE_DEFER`:** when the panel list has no match, the
  caller receives `ERR_PTR(-EPROBE_DEFER)` — neither acquire nor
  release happens. The 0058-patch text prints that return fine.

* **fwnode Handle bookkeeping.** The Sky1 linlon-dp call site reads
  its fwnode with `fwnode_find_reference(dev->fwnode, "edp-panel", 0)`,
  which **returns a counted reference on the fwnode** (`fwnode.h`
  semantics; the kernel requires `fwnode_handle_put()` to balance it).
  Neither the current 0008 call site nor the current 0058-patched
  `fwnode_drm_find_panel()` releases that fwnode reference. The
  upstream pattern (see `find_panel_by_dev()` in `drm_panel.c`) does:

```
        fwnode = fwnode_find_reference(dev_fwnode(follower_dev), "panel", 0);
…
        panel = find_panel_by_fwnode(fwnode);
        fwnode_handle_put(fwnode);
```

  i.e. `fwnode_handle_put` is unconditional on the success path; on
  the error path the fwnode ref still has to be released before the
  ERR_PTR propagates. **A re-port that ignores this is correct on
  the panel side and still leaks one fwnode ref per deferred probe**
  — that has, in practice, not bitten us because defer is rarely hit on
  ACPI-boot and the panel-fwnode ref doesn't usually outlive its owner,
  but it remains a real bug in 0008 regardless of 0058's verdict.

* **Error-path pitfalls (named explicitly, because they make a
  re-port unsafe without a real review):**
  1. Returning `ERR_PTR` for `-EPROBE_DEFER` while still holding the
     `panel_lock` — the original `fwnode_drm_find_panel()` in 0058
     releases the mutex before each `return`; a re-port must preserve
     that. (The lock is a plain `mutex_lock(&panel_lock)` with no
     `might_sleep`-style annotation beyond what `drm_panel.c` already
     uses; the existing helper has been audited for this.)
  2. Double-drop on the panel reference if the caller mistakenly does
     the same on the success path that 0058's current shape leaks on —
     i.e. `drm_panel_put` after a successful `drm_panel_get` is
     **wrong** if the helper is now refcounted. The Skypass linlon-dp
     caller currently does **neither** acquire nor release, which is
     only safe because the legacy helper returned a *non-counted*
     pointer; a refcounted re-port that retains the same call site
     produces a new leak instead of a new correctness.
  3. Wrong direction of comparison on the fwnode — upstream uses
     `dev_fwnode(panel->dev) == fwnode`, not `panel->dev->fwnode`.
     The 0058 patch uses `panel->dev->fwnode == fwnode`; on
     firmware_node-bearing devices both forms happen to be equal,
     but on ACPI-firmware-node devices the difference is real.

This is the single fact that decides everything above. Two distinct
questions are tangled in that wording:

**(a) Without patch 0058 added at all.**  We are not currently running
on rc5; the rc5 port is still being prepared. Verdict
`2026-09-27-sky1-port-7.2.8-7.3-rc5.md` confirms the patched state of
rc5 has the linlon-dp driver **loaded** by patch 0008 carrying the
`fwnode_drm_find_panel` call site — but the link
`*fwnode_drm_find_panel*` is unresolved because 0058 does not APPLY
(see §1.3). If we shipped rc5 + 0008 but not 0058, the linlon-dp
probe would fail to link (MODULE_NAME `cix-linlon-dp`) and we would
have no `fwnode_drm_find_panel` symbol at all. **Unverified at
runtime** — no kernel was booted in this session — but the link-time
fact is mechanical: `EXPORT_SYMBOL` is missing, so the call site
cannot be satisfied.

**(b) Without patch 0058 *or* its re-introduction, but instead by
moving the linlon-dp call site onto the upstream pipeline.**  This
*is* the working option, and it is the one the rest of the mainline
DRM ecosystem uses for ACPI boot. The minimum change would be:

* In the `trilin_dptx.c::trilin_dp_probe()` body, replace
  `fwnode_find_reference + fwnode_drm_find_panel` with
  `devm_drm_panel_attach(dev, panel)` once the panel is discovered
  via the standard fwnode walk, **or** drop the manual lookup and let
  the bridge layer's `panel_bridge` resolve it through
  `drm_of_find_panel_or_bridge()`.

This is mechanical work, not "porting 0058 onto rc5". The verdict on
**re-porting patch 0058 in spirit onto the refcounted API** is an
"unsafe until audited" — see §1.5(2) and §1.5(3). Until the call site
is reworked to honour both the panel reference and the fwnode
reference, an attempted re-port that *re-names* `fwnode_drm_find_panel`
to acquire a reference would, on first error path, leak that
reference exactly where the current code accidentally doesn't.
